# Liquipedia API reader

`scripts/read-liquipedia.mjs` reads Dota 2 wiki pages and searches page titles through Liquipedia's public MediaWiki API. It is a small interactive reader; [`collect-liquipedia-hero-data.mjs`](../scripts/collect-liquipedia-hero-data.mjs) remains the source-preserving collector for versioned hero and mechanics snapshots.

## Usage

```sh
node scripts/read-liquipedia.mjs page "Anti-Mage"
node scripts/read-liquipedia.mjs page "Spell Immunity" --format wikitext
node scripts/read-liquipedia.mjs page "Enchantress#Innate" --format wikitext
node scripts/read-liquipedia.mjs page "Enchantress#Rabble-Rouser" --format wikitext
node scripts/read-liquipedia.mjs hero "Enchantress" --format abilities
node scripts/read-liquipedia.mjs hero 58 --format abilities
node scripts/read-liquipedia.mjs hero "aiushtha" --format abilities
node scripts/read-liquipedia.mjs search "spell immunity" --limit 10
```

The `page` command returns JSON with the exact current wikitext, page identity, revision timestamp and permanent revision URL. Add `#<section-anchor>` to the title to select one section; `--format wikitext` prints only that section's source. A section response includes its anchor and revision ID, but the parse API does not return that revision's timestamp. The `search` command searches main-namespace pages and returns titles, snippets and article URLs. Search snippets contain MediaWiki markup.

The `hero` command resolves every hero in the local Dota roster by numeric ID, package hero key/slug, display name, or alias from `data/runtime/core.json`, then reads that hero's Liquipedia page. `--format abilities` locally converts the page's `Spellcard` and `Talents` templates into the grouped shape required by [`schema/abilities.schema.json`](../schema/abilities.schema.json). Ability `id` uses Liquipedia's `intern` engine key, and `order` follows the page's skill-card order. Cast `type` is mapped from `target0`; `behavior` retains every recognized class in that field, and `affects` retains the recognized catalog labels from `affect0`. The older `target` field is included only when every `affect0` label exactly matches a schema target. Numeric `manaCost` and `cooldown` are included only when an explicit card field contains a plain number or slash-separated rank values. `damageType` is emitted only when the card's recognized damage kinds agree. `piercesDebuffImmunity` and `breakable` use explicit yes/no fields; conditional values are omitted. `dispellable` and `dispelType` are emitted only when all buff/debuff dispel entries agree on `Any`, `Strong`, or `None`.

`tags` are inferred from available Liquipedia names, descriptions, mechanics, target/effect text, traits, and talent labels, using only keys defined by `data/tags/index.json`. These are text-derived hints; the page does not provide the package's complete semantic tag model. The `Talents` grid is emitted in tier order from tier 4 to tier 1, left then right. Each talent `Name` includes the rendered grid label and its displayed value. Since the grid does not provide a per-slot engine ID, its entries receive stable reader IDs such as `liquipedia_talent_enchantress_t4l`; these are not Dota engine ability IDs. If the article lacks a `Talents` grid, identified talent `Spellcard` rows (with their `intern` IDs) are used as a fallback. Bonus attributes are emitted when an identified `special_bonus_attributes` card exists; otherwise `bonus_attributes` is `null`. The abilities output is the schema object itself, with no provenance fields; use `hero ... --format json` when the article revision and source metadata are needed.

The same commands are available through `npm run liquipedia:read -- page "Anti-Mage"`, `npm run liquipedia:read -- hero "Enchantress" --format abilities`, and `npm run liquipedia:read -- search "spell immunity"`.

Successful API responses are cached indefinitely in the user's local cache directory so repeated reads do not re-request unchanged data. Use `--refresh` to request an update. Ordinary API requests are globally spaced at least 2.1 seconds apart; parse requests are spaced at least 30 seconds apart for processes sharing the default limiter. `--cache-dir PATH` selects a separate response cache; the request limiter remains shared. The client sends a project-specific User-Agent, accepts gzip, and reads only the `dota2/api.php` endpoint. Page reads and section reads normally use one API request each. When section metadata has no source offset, the reader makes a second parse request using the MediaWiki section index and waits for the 30-second parse interval.

Wiki text is community-authored documentation, not verified engine behavior. JSON output includes the Liquipedia contributor attribution, CC BY-SA 3.0 license, retrieval time, and terms link. Media files may have separate licenses. Follow the [Liquipedia API terms](https://liquipedia.net/api-terms-of-use), including source attribution, request pacing, User-Agent identification and API-only automated access.

## Source review

- Liquipedia's [API terms](https://liquipedia.net/api-terms-of-use) require a descriptive User-Agent with contact information, gzip-capable clients, reuse of retrieved data, and a maximum rate of one MediaWiki API request every two seconds.
- MediaWiki's [parse API](https://www.mediawiki.org/wiki/API:Parsing_wikitext) can return section wikitext by numeric section index, its [TOCData schema](https://www.mediawiki.org/wiki/API:Parsing_wikitext/TOCData) exposes section anchors, indexes and source codepoint offsets, and `prop=revid` returns the parsed revision ID. Because an explicit `prop` list omits properties not named there, the reader requests `wikitext|tocdata|revid` together and slices the selected source section locally. It uses `section=<index>` with a pinned `oldid` and `prop=wikitext|revid` only when the page response does not provide a usable source offset. Liquipedia's API terms give `action=parse` the stricter limit of one request per 30 seconds; the shared limiter enforces it.
- Liquipedia's [API landing page source](https://github.com/Liquipedia/Liquipedia.net-page/blob/master/api.php) lists per-wiki API endpoints and links its terms. [`pywikibot/site_detect.py`](https://github.com/Liquipedia/pywikibot/blob/54a5736f5e07acf305fda4d2d2ffc075ae577738/pywikibot/site_detect.py#L149-L171) derives a wiki's `api.php` path from its server and script path. The community [`liquipedia_family.py`](https://github.com/FO-nTTaX/liquipedia-scripts/blob/10acc21232b874042022dd33fe48c288b39c3f51/pywikibot/liquipedia_family.py#L9-L21) confirms Liquipedia's per-game API path and gzip support.
- The [Liquipedia search tool](https://github.com/FO-nTTaX/tools.liquipedia.space/blob/master/view/search.php#L4-L28) uses `action=query&list=search` and the `srlimit`/continuation parameters. This reader returns one bounded result page and does not crawl further pages.
- The structured `hero --format abilities` path uses the same `action=query&prop=revisions&rvslots=main&rvprop=ids|timestamp|content` read as `page`, then parses the cached wikitext locally. It does not need an additional parse request for a full hero page.
- The supplied [`Lua-Modules/javascript/Main.js`](https://github.com/Liquipedia/Lua-Modules/blob/5092d96973252e4e6366110b43d730c7ce38e59f/javascript/Main.js#L1-L39) is explicitly a test-only `mw.Api` mock. The linked `UpdateMessageApiModule`, `Dota2WebApi` toolbar, `FlaggedRevs` hooks, and [`reviewbot.js`](https://github.com/FO-nTTaX/liquipedia-scripts/blob/10acc21232b874042022dd33fe48c288b39c3f51/js%20console%20bots/reviewbot.js#L19-L35) examples concern writes, review actions, or match-data integrations; this reader does not call those endpoints or authenticate.
- Other reviewed examples: [`mediawiki_session.py`](https://github.com/Liquipedia/Lua-Modules/blob/5092d96973252e4e6366110b43d730c7ce38e59f/scripts/mediawiki_session.py#L37-L94), [`UpdateMessageApiModule.php`](https://github.com/Liquipedia/LiquipediaMediaWikiMessages/blob/c840852d7970ff812bac2fef4141d71cc28641cd/src/Api/UpdateMessageApiModule.php#L9-L55), [`WikiList.php`](https://github.com/Liquipedia/TrendingMenu/blob/6b08d5b9e29b1e15edc8b4777f916443df720c51/src/Api/WikiList.php#L8-L22), [`FlaggedRevsApiHooks.php`](https://github.com/Liquipedia/FlaggedRevs/blob/99cf3aa519c7bea2f8c1a35aae6a8e12182766f3/api/FlaggedRevsApiHooks.php#L8-L35), [`ext.dota2WebApi.toolbar.js`](https://github.com/Liquipedia/Dota2WebApi/blob/f185a3705c1ca400f3b34478f413d9349e2651f2/resources/scripts/ext.dota2WebApi.toolbar.js#L132-L169), [`_optionset.py`](https://github.com/Liquipedia/pywikibot/blob/54a5736f5e07acf305fda4d2d2ffc075ae577738/pywikibot/data/api/_optionset.py), [`MainHookHandler.php`](https://github.com/Liquipedia/LiquipediaMediaWikiMessages/blob/c840852d7970ff812bac2fef4141d71cc28641cd/src/Hooks/MainHookHandler.php#L58-L68), [`lpuser-editcounter.php`](https://github.com/FO-nTTaX/liquipedia-scripts/blob/10acc21232b874042022dd33fe48c288b39c3f51/lpuser-editcounter.php#L4-L24), and [`prizepoolbot.py`](https://github.com/FO-nTTaX/liquipedia-scripts/blob/10acc21232b874042022dd33fe48c288b39c3f51/pywikibot/prizepoolbot.py#L3-L15). They illustrate MediaWiki query or authenticated write flows but do not define a separate public Dota knowledge API.
